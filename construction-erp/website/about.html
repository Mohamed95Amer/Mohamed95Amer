About Majal, and how it is put together

Majal is a construction and facilities-management suite built on Odoo 18 Community Edition. The source is public, the upstream dependencies are pinned by commit, and every module states its own licence in its manifest. This page says what is in the stack, under what terms, and how to run it yourself.

What the stack is made of

Four layers, each pinned so a build can be reproduced rather than approximated.

The four layers of a Majal build and where each one is pinned.
Layer What it contributes Pinned in
Odoo 18.0 Community Edition The ERP backbone: accounting, purchasing, inventory, HR, timesheets, projects, maintenance, the portal and the web client ODOO_PINNED_SHA, fetched by scripts/fetch-odoo.sh — not committed
OCA modules Field service, DMS, helpdesk, contracts, tier validation, MIS Builder, responsive web, Gantt timeline oca-repos.yml → vendored into oca-addons/
Community third-party apps Full accounting — financial statements, asset management, budgets, recurring payments, customer follow-ups — from the Odoo Mates community accounting suite third-party-repos.yml → vendored into third-party-addons/
Majal modules The product itself: 38 construction, facilities and platform modules custom-addons/, in this repository

Reuse over rebuild

Where a good free module already exists, Majal vendors and pins it instead of writing another one. Full accounting is the clearest case: financial statements, asset management, budgets, recurring payments and customer follow-ups are otherwise Enterprise-only features, and the LGPL-3 Odoo Mates community accounting app supplies them. Facilities work orders sit on Odoo's own maintenance app rather than on a parallel model, and the Gantt is OCA's web_timeline.

The consequence worth naming: material control books stock through Odoo's real inventory, and site stores are real stock locations. There is no second inventory keeping its own opinion of what is on site.

Two libraries that are not committed

The 3D BIM viewer needs web-ifc and three.js, fetched once by scripts/fetch-bim-libs.sh (or the PowerShell equivalent). web-ifc's browser build alone is 6 MB, so it is pinned and fetched rather than vendored. Everything else about a BIM model — the element index and its linked RFIs, defects, tasks and bill items — works without them, and the viewer says so on screen if they are missing.

Licensing

Odoo 18 Community Edition is licensed under the GNU LGPL version 3. OCA modules are licensed individually under LGPL-3 or AGPL-3. The Odoo Mates community accounting modules are LGPL-3.

Majal's own modules are declared LGPL-3, with two exceptions: facility_contract and facility_inventory are declared AGPL-3, because they build on OCA's AGPL-3 contract lineage. Every module's __manifest__.py and its source headers state the licence that applies to it; the module table on the features page lists all thirty-eight with their declared licence.

The browser libraries used by the BIM viewer keep their upstream terms — web-ifc under MPL-2.0 and three.js under MIT — and their pinned revisions are recorded in custom-addons/construction_bim/static/lib/SOURCES.md.

What AGPL means for a deployment

Anyone who interacts with modified AGPL-covered software over a network must be offered the corresponding source. For this build that offer is the repository below, and the product links to the same offer from its own /majal/legal/open-source page. A deployer running a different repository or release has to update the offer and keep it available to remote users.

Odoo Enterprise code is not used and must not be copied without a valid subscription. Odoo is a trademark of Odoo S.A.; Majal is not affiliated with or endorsed by Odoo S.A.

The full third-party notice lives in NOTICE.md in the repository. It is a notice, not legal advice — a commercial deployment should get its exact combination and distribution model reviewed.

Running it yourself

Majal is a normal Odoo add-ons tree. Nothing phones home, nothing needs a licence key, and there is no feature gated behind a subscription. The two supported paths are Docker and bare metal; there is also a devcontainer configuration if you would rather it boot in a browser.

Docker

Clone the repository, copy .env.example to .env, and bring the stack up: 

cd construction-erp
cp .env.example .env
docker compose up -d --build

Then initialise a database with the modules you want — the repository README carries the full install list, including the accounting suite and --load-language=ar_001 for Arabic — and restart the container. Odoo comes up on port 8069.

Bare metal

cd construction-erp
./scripts/fetch-odoo.sh                 # pinned shallow clone into vendor/odoo
pip3 install -r vendor/odoo/requirements.txt -r requirements-oca.txt
./scripts/init-db.sh erp                # create the database and install modules
./scripts/run-local.sh -d erp           # run the server

Tests

The suite ships its own tests — 44 test modules containing over five hundred test methods, run against a real database rather than mocked: 

./scripts/run-tests.sh all              # or a single module name

Several of them exist because a specific assumption turned out to be wrong. The approval engine has a test asserting that a delegate holding only site-engineer rights can approve a bill of quantities without holding write access to it; the PWA icon has a test that parses the served SVG rather than trusting the comment above it.

Before you put it on the internet

Self-hosting an ERP is an operational commitment. The repository's security baseline lists what has to be true before exposure: a real HTTPS web.base.url, working outgoing mail before enabling email two-factor authentication, a maintained reverse proxy with proxy_mode and TLS termination in front of port 8069, demo users and demo data removed, and encrypted off-machine replication of the recovery points. Local recovery points alone do not protect against losing the host or the account.

On demo data

majal_demo installs a two-company acceptance dataset and nine role personas. It is for isolated demo and QA databases and should never be installed for a production client.

For integrators

Majal exposes two surfaces. The first is Odoo's own external API — XML-RPC and JSON-RPC over the standard ORM, reaching every Majal model, field and public method. This is what most integrations use. The second is a small, deliberate set of Majal HTTP routes for asset tag scanning, the offline field app, the customer and subcontractor portal, CSV export and the WhatsApp webhook. There is no separate REST API, no GraphQL endpoint, and no /api/v1/... namespace — if a route is not documented, it does not exist.

Authentication

Every RPC call authenticates with (database, uid, password), where the password may be a developer API key instead of the account password. An API key is required once a user has MFA enabled — majal_security switches that account to key-only authentication over RPC, so an integration built against a plain password breaks the day its account enrols in two-factor. Keys are minted from the UI, shown once, and stored only as a hash.

Why it was built this way

Four platforms set the bar Majal was designed against, and the design notes are explicit about what each of them does better. Procore is the enterprise system of record. Fieldwire is the field-first tool crews actually open. PlanRadar is pin-on-plan documentation. IBM Maximo is enterprise asset management.

The gap they share is the interesting one. Field tools capture excellent data and then stop: the defect, the daily log and the inspection never reach the ledger, so the commercial position is reassembled by hand every month in a spreadsheet. Odoo Community supplies the ledger for nothing. What was missing — from every field tool and from Odoo core alike — is the commercial layer between them: bill of quantities to subcontract to variation to progress claim with retention, and the cost value reconciliation that ties them together.

That is the piece Majal adds, and the reason the rest of it exists on the same database rather than beside it.
