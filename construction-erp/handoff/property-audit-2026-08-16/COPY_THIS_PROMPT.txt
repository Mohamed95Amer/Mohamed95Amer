TWO RULES THAT REPEATEDLY COST TIME ON THIS PROJECT

1. A clean install proves nothing about whether a feature works. On the
   dashboard branch, four separate features installed perfectly and were
   broken, and the Python suite was green through every one. The most recent:
   a dashboard panel wired with no context took the ENTIRE board down with a
   client error dialog, and no test saw it. If you touch UI or JS, drive it in
   a browser (Playwright, executable_path=/opt/pw-browsers/chromium, wait on
   .o_main_navbar, never networkidle) and listen for pageerror.

2. Read the API before writing against it. Assumed field names have caused
   most of the defects on this project. Two recent examples, both of which
   made a test pass while measuring nothing: res.users.share is computed from
   group membership, so share=True on create is silently discarded; and
   fields.Image runs every write through PIL, so arbitrary bytes raise before
   any logic under test is reached.

Also run scripts/init-db.sh, not only scripts/run-tests.sh. The suite never
loads a language; init-db.sh loads ar_001, and a malformed .po entry has taken
the whole install down while the suite stayed green.

Before you start, run: git status --short && git log --oneline -5
Report what you find before changing anything.
