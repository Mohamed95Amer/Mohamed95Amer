# Handoff — six changes on `codex/odoo19-ui-enhancement`

Written for Codex, who owns deployment. Everything below is application-layer.
**Nothing in `infrastructure/` was touched, no server was accessed, and
`wip/local-2026-07-31` was not merged.**

Range: `5080eb6..dce4b70` — 58 files, +3914/−124.
Suite: **553 tests, 0 failed** (was 517 at the start of the range).

---

## Deploy in one line

```bash
odoo -d <db> -i majal_workforce \
     -u majal_administration,construction_ui,construction_base,construction_bim,construction_report,majal_documents \
     --stop-after-init
```

Then restart. Detail on why each module is in that list is under each change.

**Two things that will bite if skipped:**

1. `-u`, not a restart. Three of these changes are data — a migration, menu
   actions, and new views — and a bare restart applies none of them.
2. `majal_administration` **must** be upgraded, not just restarted. Its
   migration backfills what every access level grants. Without it, an existing
   database comes out with empty levels and reduces every user to a bare login
   on their next access change.

## 1 · `754f8c3` — BIM viewer showed no elements

`custom-addons/construction_bim/`

The header counted every element in the model while the side panel was fed a
linked-only `search_read`, so a freshly indexed model read "120 elements"
beside an empty panel. `viewer_payload` now returns every
`construction.bim.element`; unlinked ones already carry a `link_bucket` of
`none`, so the existing filters separate them, and a new **Unlinked** filter
makes that bucket reachable.

`linkedByGlobalId` stays linked-only — it drives the 3D colouring, and
building it from the whole payload would have drawn the entire model as
attached to something. A second map holds every element, which also fixed
indexed quantities being invisible for unlinked elements.

Files: `models/bim_model.py`, `static/src/viewer/bim_viewer.{js,xml}`,
`tests/test_bim.py`.
**Deploy:** code only. Restart is enough, though `-u construction_bim`
rebuilds the asset bundle and does no harm.

## 2 · `591c038` — Access levels are configurable per company

`custom-addons/majal_administration/` — **has a migration**

What a level granted lived in three Python dicts, so renaming a level or
changing its permissions meant a code change. It is now data on
`majal.access.role`: groups always granted, groups granted with construction
access, groups granted with facilities access. The six standard levels ship
with exactly the old mapping; a company takes a copy (**Customise for this
company**) and edits it without affecting anyone else. Changing a level
updates everybody already holding it.

A level is a permission grant, so it is the most dangerous editable record in
the system. An administrator cannot put administration groups into one, grant
a group they do not hold themselves, touch another company's levels or the
standards, or edit a level at or above their own. Each guard has a test that
fails when the guard is removed.

Files: `models/access_role.py`, `models/res_users.py`,
`data/access_roles.xml`, `views/access_level_views.xml`, `views/menus.xml`,
`security/ir.model.access.csv`, `tests/test_administration.py`,
`migrations/18.0.1.1.0/post-migrate.py`, manifest version → `18.0.1.1.0`.

**Deploy:** `-u majal_administration` — required. The migration is idempotent
and skips any level already configured, so re-running an upgrade cannot undo a
company's work. Verified against a database installed at the previous version.

New screen: **Administration → Access Levels**.

## 3 · `bc1e6a9` — Navigation moved into a sidebar

`custom-addons/construction_ui/static/src/sidebar/`

The top bar holds about nine entries; Construction has eighteen sections and
forty-five screens under them, so everything past the ninth lived behind a `+`
or a hover menu, and nothing on screen could tell you which section you were
inside.

The navbar is **kept** — it still carries the breadcrumbs, the search and the
systray, and gives up only the section menu it never fitted. Sections expand
in place, the current screen stays highlighted, and both preferences survive a
reload: open sections in local storage keyed by xmlid (ids are not stable
across databases), the current screen in session storage.

Collapsing folds to the app rail alone, not a narrower tree: sections carry no
icons, only apps do, so a collapsed tree would have been a column of identical
dots. Below the medium breakpoint the sidebar stands down and Odoo's burger
menu takes over, so the phone layout is unchanged.

Files: `static/src/sidebar/majal_sidebar.{js,xml,scss}`, manifest.
**Deploy:** `-u construction_ui` to rebuild the asset bundles.

## 4 · `0e582f8` — Avatars and the top-bar icons

`custom-addons/construction_ui/`, `custom-addons/construction_base/`

**Avatar.** Odoo draws one initial on a colour hashed from the name *and the
creation timestamp*, so it lands anywhere on the wheel and changes if a record
is recreated. Now two initials on a fixed six-colour palette taken from the
back end's own, all deep enough that white clears AA, seeded on the name alone
so a person keeps their colour after a restore. Accounts with no name fall
back to a Majal figure. Odoo's demo accounts ship with stock photographs of
strangers — cleared, **as demo data**, so a real deployment's uploaded photos
are untouched.

**Systray.** Removed `web_responsive`'s App Menu Preferences droplet: it tunes
the app drawer, which the sidebar replaced, leaving an unlabelled icon that
opened a user form. Removed inside `whenReady` because nothing orders this
module against `web_responsive`, and removing an entry before it is added does
nothing. Kept messages, activities, and the tier-review counter — that one is
real, `construction_submittal` uses `base_tier_validation`.

**Added an approvals counter.** The approval inbox is the queue the product is
built around and was the only one without one. Its action names its `views`
explicitly, because the browser is handed it directly rather than resolving it
from a server action, and without them the client throws while preprocessing —
the counter would have looked broken rather than the action.

Files: `construction_ui/models/res_partner.py`,
`static/src/systray/approvals_systray.{js,xml}`, `static/img/majal_avatar.png`,
`data/demo_avatars.xml`, `construction_base/models/approval_request.py`.
**Deploy:** `-u construction_ui,construction_base`. Demo-avatar clearing only
applies to databases installed with demo data.

## 5 · `214a3bf` — Menus go to records, registers got filters

`custom-addons/construction_ui/`, `custom-addons/majal_documents/`

**Filters.** Of 63 browsable registers, 35 had no search view at all — no
filters, no group-by — including the ones carrying money. Twelve now answer
the questions actually asked of them: what is open, what is overdue, what is
certified but not invoiced, which subcontracts still hold retention.

Two needed care and are worth knowing about: a drawing revision has no `name`
(it is identified by its drawing and its letter), and
`subcontract.amount_retained` is computed without being stored, so it cannot
be searched at all — that filter goes through the payment certificates.

**Menus.** Every leaf menu opened a workspace dashboard first, so reaching a
bill of quantities cost two clicks and the breadcrumb read "Submittals /
Submittals". Worse, pairs collided: Forms and Form Templates both opened the
inspections hub, BOQ and BOQ Analysis both opened the BOQ hub — two entries,
one screen. **38 register menus** now open their records. The five workspaces
keep their dashboards and each section still carries an Overview entry.

**Assistant name.** `construction_ui` wrote an Arabic name over the one
`majal_branding` had already set, so on an English database every chatter
thread was authored by a name nobody could read — while the message body said
"Majal Assistant", because `majal_branding` substitutes the English name into
message text. Two modules owned one identity; the one that also gives the
assistant its avatar keeps it.

Files: `construction_ui/views/register_search_views.xml` (new),
`views/workspace_hub_views.xml`, `views/majal_branding.xml`,
`majal_documents/views/sheet_views.xml`, manifest.

**Deploy:** `-u construction_ui,majal_documents`. The menu repointing writes
new action values onto menus owned by *other* modules, so it takes effect on
`-u` and not on a restart. **If only restarted, the menus still show hubs.**

## 6 · `dce4b70` — Workforce allocation

`custom-addons/majal_workforce/` (new), `custom-addons/construction_report/`

The product had no workforce: `hr.employee` was untouched by all 37 modules.
But project membership was **already the access primitive** —
`tenant_security.py` puts `majal_member_ids` on projects and
`member_user_ids` on locations, and every generated rule says that below rank
40 you see only records whose project or location names you.

So `majal.allocation` (person + project *xor* location + role + dates + %)
is the source of truth, and those membership fields became a **projection** of
it. **`tenant_security.py` is not modified.** Neither are the four
hand-written domains in `majal_documents` that read
`project_id.majal_member_ids` directly. People without a login are allocated
and counted but project nothing.

Three decisions that matter if you review the code:

- **`majal_manager_id` is never projected.** Every rule compares it with `=`,
  so it holds one person; two lead allocations would take turns overwriting
  each other while the rules followed whoever wrote last.
- **Location allocations cascade down the tree.** Facilities rules reach an
  asset by its *exact* location, and "a location any of whose ancestors names
  me" is not expressible as a domain leaf, so the inheritance is materialised
  by the projection. Without it a technician on a building is blind to its
  rooms.
- **Nobody is stripped mid-approval.** Approval steps are not project-scoped
  but the documents they gate are, so revoking someone with a pending step
  leaves it in their inbox pointing at a record they cannot open — stuck, and
  looking healthy. Access is held until it resolves; ending an allocation
  offers a delegation.

A nightly cron applies date changes (a date passing is not an event, so
nothing lapses on its own), a grace period keeps a departure from being a
cliff, and every removal is posted to the project's chatter.

Also fixes a **pre-existing bug** found while wiring the Team tab: the
read-only CVR report was the default form for every construction project,
because Odoo resolves a default view by priority *then by name* and "cvr"
sorts before "form". Opening any project gave a report with no tabs and no way
to edit. Demoted and bound to its own action.

**Deploy:** `-i majal_workforce -u construction_report`. The install hook
backfills one allocation per existing project/location member, so no team is
lost. Registered in `scripts/run-tests.sh` and `scripts/init-db.sh`.

New screens: **Team** tab on projects and locations, **Allocations** tab on
employees, **Workforce** menu under Construction and Facilities.

`docs/reuse-decisions.md` already flags timesheets as reuse-not-rebuild — that
